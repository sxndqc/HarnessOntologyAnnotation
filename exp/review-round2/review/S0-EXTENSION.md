# 给已有条目补上 baseline 的两份标注

## 背景

`review/items/<doc>.<from>-<to>.json` 是上一轮审阅的条目：每个条目是一个比较点，`choices` 把 gold 和 6 个系统（`s1f/r1`、`s1f/r2`、`s3/r1`、`s3/r2`、`a2/r1`、`a2/r2`）分到各个选择里，每个选择有 status（`ok` 正确 / `minor` 可接受但略差 / `bad` 错 / `open` 定不了）。格式和检查方法见 `review/REVIEWER.md` 的"条目"和"写完后的检查"两节，先读这两节和"已经定下来的规则"一节。

这一轮多了一个 baseline 设定 `s0`（整篇一次标完，guideline 只有一句话，没有工具），有两次运行 `s0/r1`、`s0/r2`。你负责的文档已经有它们的输出，但已有条目里没有它们。**你的任务是把 `s0/r1` 和 `s0/r2` 加进你负责的文档的每一个已有条目里**，让每个条目重新是 9 个名字各出现一次。

## 怎么做

```bash
python3 pipeline/mechdiff.py zh-0028 3                               # 这一句 9 份标注不一致的地方
python3 pipeline/show_sentence.py zh-0028 3 --only gold,s0/r1,s0/r2   # 原文
python3 pipeline/show_sentence.py zh-0028 --grep 恢复-02              # 哪些标注的哪些句子里有这段文字
```

对每个条目，看 `s0/r1`、`s0/r2` 在这个比较点上各自怎么标的：

- 和某个已有选择一样：把名字加进那个选择的 `systems`。如果那个选择有 `grep`，这段文字必须也能在 s0 这一句的标注里原样找到（检查脚本会核对）；找不到说明它其实不是同一种标法，或者 grep 写得太具体：是前者就另立选择，是后者（意思相同只是写法细节不同）就把 grep 改成几份标注都有的文字，或者删掉这个选择的 grep。
- 和已有选择都不一样：新加一个选择，`label` 用它的写法，status 按 `review/REVIEWER.md` 的标准和"已经定下来的规则"判断；能写就写 `grep`。
- 这一句里 s0 没有相应的节点或关系：归到已有的"没有标 / 没有这个节点"一类的选择；没有这类选择就新加一个。它是因为上游漏了一个节点而连带缺失、且那个漏节点已经在别的条目里记过时，status 写 `open`，否则按实际情况写 `minor` 或 `bad`。
- s0 的某一句没有有效的图：新加选择"没有有效标注"，status `bad`。

几种情况的处理：

- **s0 全篇重复的同一种习惯**（例如时间关系的方向一律写反、conceiver 不挂在 author 下）：只在这篇文档里它第一次出现的那个条目里按实际判（`bad` 或 `minor`）；之后的条目里，如果 s0 的差别只是这同一个习惯，新加的选择 label 写成"（同一习惯：……，见第 N 句）"，status 写 `open`，免得一个习惯被算很多次。
- **已有标注都一致、所以没有条目的地方 s0 标错了**：不新建条目，在回复里列出来（第几句、什么错）。
- **已有的 grep 太具体、对不上 s0**：优先把 grep 放宽成几份标注都有的文字；放宽后没有区分度就删掉这个选择的 grep。不要为此把意思相同的标法拆成两个选择。
- **label 里带的附带细节不同**（例如"连到第 3 句"而 s0 连到第 1 句）：按这个比较点真正在比的东西判断是不是同一种选择；细节上的差别如果原来的判断认为有影响（例如"不是最近的提及"判 `minor`），就另立选择并沿用那个判断。
- `mechdiff.py` 的输出很长时，用 `| grep "s0/"` 只看带 s0 的行，再对着原文核对。

其他不要动：已有 6 个系统和 gold 的归属、status、`best`、`text`、`fix`、`before_*` 字段都保持原样。唯一的例外是你在核对时发现已有的归属明显写错了（某个系统被放进了不是它的选择），这种改掉并在回复里列出来。不新建条目，不删条目。`best` 只在你新加的选择明显比原来的 `best` 更好时才改（很少见）。

文档级的条目（时间、模态、共指）通常是归并过的现象（"报道事件相对文档时间""跨句共指有没有连"），按同样的现象看 s0 属于哪一类。

建议一句一句做：先 `mechdiff.py` 看这一句，再把这一句的所有条目改完，改几句跑一次检查。

## 检查

每个文件都要过：

```bash
python3 pipeline/items.py check review/items/zh-0028.01-12.json
```

必须 0 errors（9 个名字各出现一次、grep 都对得上、fix 仍然能执行）。

只改你负责的文档的 `review/items/<doc>.*.json`，不改 `.notes.md` 和别的文件，不运行 `items.py build`、`score.py`、`build.py`。直接改 JSON（建议用小脚本按条目位置修改，改完重新读一遍确认）。临时脚本放在会话临时目录下你自己新建的子目录 `s0-<文档号>/` 里。

## 回复

几行即可：处理了多少条目；s0/r1、s0/r2 各有多少条落在 `ok` / `minor` / `bad` / `open`；新加了多少个选择；有没有改已有的归属（列出来）；各文件检查是否 0 errors。
